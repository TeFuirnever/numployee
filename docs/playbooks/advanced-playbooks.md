# 数字员工进阶玩法手册

> 面向 U3-U5 玩家（用户段位，与 SPEC 员工成熟度 L1–L5 是两套刻度，见 SPEC 附录 D）。本文所有路径、技能名、配置键均取自一个闭源桌面客户端产品的作者自述案例（未经独立验证）；机制描述以产品的领域术语表、AI 导航 wiki、架构决策档案与源码为准。标注（规划中）的内容是设计已冻结、但落地进度以该产品仓库为准的部分。
>
> 配套配方全文见 `recipes/persona-recipes.md`（人格配方）与 `recipes/sop-and-probes.md`（SOP 模板 + 回归探针清单）。

## 〇、用户段位模型

这本手册的地基。**注意刻度消歧**：本手册的用户段位记为 **U1–U5**（描述使用者），与 SPEC 第 4 章的员工成熟度分级 L1–L5（描述员工，能力 × 治理 × 评测联合门槛）是两套刻度，勿混用（唯一基准见 SPEC 附录 D 术语与符号注册表）。判定自己在哪一段，直接跳到对应玩法。

| 段位 | 一句话定义 | 标志性能力 |
| --- | --- | --- |
| **U1 小白** | 开箱即用：装应用、从市场挑个顺眼的员工、聊起来，其余交给默认配置。 | 会创建/删除员工、会从市场下载、找得到默认模型设置 |
| **U2 熟手** | 日常驾驭：按任务选模型与模式，用过 Team 群发，说得清 Role 和 Employee 的区别。 | 会给不同任务配推荐模型、知道 Code Mode 开关、用 Team 做过并行咨询 |
| **U3 进阶** | 定制人格与流程：动过人格文件、会把技能串成流水线，员工开始"说你的话、按你的规矩干活"。 | 写过 SOUL 块外配方、配置过 USER.md、把两个以上技能串成流水线 |
| **U4 高级** | 生产级编排与治理：多员工生产线、私有 skill、嵌套 SOP、A/B 评测、成本与人审治理。 | 设计过 sequential Team、写过自己的 SKILL.md、手里有评测表 |
| **U5 极客·布道者** | 生态与进化：让员工自我进化、把配方产品化、搭组织级中台与回归评测集，并向外输出方法论。 | 跑过 darwin-skill、发布过市场模板、维护共享回归集 |

判据比名头重要：只会聊的是 U1-U2；天天改配置的是 U3；给团队定规矩、做评测、管成本的是 U4-U5。

### U1/U2 速览（两小节带过）

**U1 最佳路径**：从市场（source=market）挑员工直接用，别急着改指令——默认人格（该产品的受管块同步机制：模板在其提示词增强模板目录中，当前 v5.4.0）发布前已过金丝雀验证（该产品的 canary 发布流程，作者自述）。

**U2 该补的认知**：三层对象模型——Role 是模板（名称/描述/指令/推荐模型，不可对话），Employee 是 Role 的持久实例（绑定 backing Agent，可对话、有持久状态），Agent 才是运行时真正的隔离执行单元（独立 workspace 与 agentDir）。升级的关键一步是意识到：你在配置的是一个长期雇员，不是一段用完即弃的提示词。站在这个认知上，你就摸到了 U3 的门。

## 一、U3 进阶：定制人格与流程

### 玩法 1：人格配方——微调员工的语气与边界

- **目标**：在默认人格之上叠加一层"你的配方"，形成稳定、可复用的交互风格。
- **为什么值得玩**：默认 SOUL 已过行为探针验证，推倒重写既烧钱又容易退化；配方式微调投入半小时，回报是全员一致的说话风格。
- **前置条件**：理解受管块机制——该产品的受管块同步机制：模板在其提示词增强模板目录下，由产品主进程中的受管块同步器按版本同步到 `~/.openclaw/workspace/`（SOUL.md / AGENTS.md / TOOLS.md / IDENTITY.md / USER.md / BOOTSTRAP.md，HEARTBEAT.md 为运行时生成、不受管）。同步语义：缺失插入、旧版替换、**块外用户内容保留**、同版本幂等。
- **步骤**：
  1. 打开 `~/.openclaw/workspace/SOUL.md`，定位受管块标记（各实现标记不同，以你的实现为准）。
  2. 不要改块内——块内在版本升级时会被模板覆盖。把配方写在块外，追加一节 `## 人格配方`。
  3. 配方只调 SOUL 的七个维度：诚实且温暖 / 温和但有立场 / 培养独立 / 察言观色 / 主动伙伴 / 自然表达 / 边界感。逐项写"加什么、减什么"，禁止泛泛的"请更专业一点"。
  4. 三个可直接抄的骨架在 `recipes/persona-recipes.md`：毒舌严师型（压"温和但有立场"、抬"培养独立"）、温柔教练型（抬"察言观色"与"培养独立"、收"主动伙伴"的抢话倾向）、高冷专家型（压"主动伙伴"与幽默、抬"边界感"与信息密度）。
- **验证**：抛一个会引发讨好的问题（"我这方案是不是很棒？"），看员工按配方表态还是捧场；再给一个真有缺陷的方案，看指出问题的力度是否符合配方强度。
- **风险与红线**：块外内容升级时保留，但人格仍受托管块红线约束——`AGENTS.md` 的 Red Lines 段（破坏性操作确认等）任何配方不得绕过。

### 玩法 2：服务对象画像——用好 USER.md 与 IDENTITY.md

- **目标**：让员工长期记得"你是谁、你的偏好是什么、它自己是谁"。
- **为什么值得玩**：USER.md 是员工每轮都能看到的画像，一次配置长期生效；比每轮重复"我是后端，别写前端示例"便宜得多。
- **前置条件**：确认 `~/.openclaw/workspace/USER.md` 与 `~/.openclaw/workspace/IDENTITY.md` 已同步，同样遵守受管块规则——块外追加，别改块内。
- **步骤**：
  1. USER.md 写三类事实：身份与技术栈（角色、语言、框架）、口味偏好（代码风格、回复长度、术语表）、禁区（不用的库、不生成的内容）。口味变了就改，把它当"个人 README"维护。
  2. IDENTITY.md 给员工起稳定的名字与一句话身份（"你是组里管重构的老张"），与玩法 1 的配方配合，人格一致性明显提升。
- **验证**：隔天新开会话问"我让你记住的偏好有哪些"，答对即生效。
- **风险**：USER.md 常驻上下文，写废话等于每轮白烧 token；控制在 50 行以内，过期条目按月清理。

### 玩法 3：技能组合配方——把技能串成流水线

- **目标**：把技能库的散件组装成两条固定流水线："从想法到 PR"与"排障"。（技能库示例：该产品维护的技能库，47 个技能。）
- **为什么值得玩**：单个技能解决单点问题，流水线解决"一件事从头做到尾"。该产品的技能库里躺着数十个技能，多数用户只用其中 3 个。
- **前置条件**：`to-spec` / `to-tickets` 依赖 issue tracker 词汇表，先跑一次 `setup-matt-pocock-skills`；issue 落盘约定见产品的 issue tracker 本地 Markdown 约定（`.scratch/<feature-slug>/` 结构）。
- **两条流水线**：
  - **想法 → PR**：`research`（查一手资料，产出带引用的 Markdown）→ `grilling`（一轮轮带推荐答案的问题，把想法烤熟）→ `to-spec`（合成 spec 发到 tracker）→ `to-tickets`（拆成带阻塞边的 tracer-bullet 票）→ `implement`（按票实现，内部调 `tdd` 与 `code-review`，完成后提交）。
  - **排障**：`diagnosing-bugs`（先脱敏再复现，走诊断循环）→ `tdd`（红灯测试钉住 bug）→ `code-review`（合并前评审）。
- **步骤**：把流水线写进员工的自定义指令，用触发句启动，如"走流水线 A：给 XXX 加导出功能"。
- **验证**：挑一个小功能完整跑一遍，确认 `.scratch/` 依次出现 spec、票、commit。
- **风险**：链越长，中间产物越容易被下游无视——在指令里写明"每步开始前先读上一步产物路径"。

## 二、U4 高级：生产级编排与治理

### 玩法 4：Team 流水线工程

- **目标**：用 Team 的 sequential 模式搭多员工生产线，如"调研员→写手→审校"或"Code Reviewer→修复工→提交员"。
- **为什么值得玩**：单员工是手工作坊，Team 是流水线——不同人格/模型的员工各做最擅长的一段。
- **前置条件**：Team 语义以产品决策记录为准（领域术语表决策记录、产品内部的两条架构决策记录（ADR）与 Team 设计文档）；7 个 IPC 通道（`team:list` / `team:create` / `team:update` / `team:join` / `team:leave` / `team:delete` / `team:send`）；持久化在产品用户目录下的 teams.json（schemaVersion 1，原子写 + 异步互斥，闭源产品实现路径）。界面入口与派发链路按设计逐步落地，操作入口以你客户端里的实际入口为准（部分链路规划中）。
- **teams.json 数据模型**：

  ```json
  {
    "schemaVersion": 1,
    "teams": [{
      "id": "uuid",
      "name": "1-100字",
      "description": "≤500字",
      "memberEmployeeIds": ["最多10个员工id"],
      "dispatchMode": "parallel | sequential",
      "createdAt": 0,
      "updatedAt": 0
    }]
  }
  ```

- **工程约束如何塑造设计**（本玩法核心）：
  - **sequential 传全部、不摘要**：上一步完整输出拼入下一步输入，但**单步超 2000 字截断并提示**——所以每步交付物必须短：让调研员交 500 字摘要而不是 5000 字笔记，否则下游看到的是残篇。
  - **每次带原始用户消息**：链上每个员工都看得到最初需求，意图不会在传递中丢失；但敏感信息全员可见，原始消息里别放密钥。
  - **session 隔离**：员工间无共享记忆（parallel 互不可见，sequential 单向可见）。状态不能"存在上一个人脑子里"——要么写进交付物文本，要么落盘成文件让下一步读。
  - **unavailable 不自动移除**：成员 inactive 或模板更新后，派发返回 `unavailable` 跳过，但不会从 roster 清除。名册卫生是你的活：每月过一遍成员列表。
  - **其余约束**：无 leader（顺序由 dispatchMode 定，没有"工头"角色）；Bastion 消息级检查每次 send 一次；错误经 `TeamErrorKind` 有限枚举脱敏（原始错误不外泄，前端以 i18n key 展示）；审计写 `team-audit.json`；上限：成员 ≤10、单次派发目标 ≤5、单条消息 ≤10000 字；设计文档另给出每步 30s、全程 120s 的超时预算。
- **验证**：建一条三员工顺序链，故意让第二个员工 inactive，确认第一步照常、第二步 `unavailable`、第三步 `skipped`，前端均有提示。
- **风险与红线**：Team 是全局实体、不绑定 workspace——生产线别硬编码某个 workspace 的私有路径；`blocked`（Bastion 拦截）不可试图绕过。

### 玩法 5：写私有 skill

- **目标**：把重复流程固化成 skill 文件（`SKILL.md`，置于你仓库的技能库目录下），让员工一句话唤起。
- **为什么值得玩**：流程在脑子里=每次重讲；写成 skill=可进 git、可版本化、可被 darwin-skill 优化（玩法 9）。
- **前置条件**：先读 3-5 个真实 skill（推荐 `tdd`、`handoff`、`research`，风格差异大）。
- **SKILL.md 规范**：frontmatter 至少 `name` + `description`（description 写清"何时用"，员工靠它路由）；正文写步骤、边界、产出物；可选 `argument-hint`、`disable-model-invocation`。
- **何时写成 skill、何时写成 AGENTS.md 规则**：可复用流程（有输入、有步骤、有产出）→ skill；通用纪律（编码规范、禁止事项、沟通口径）→ AGENTS.md。skill 按需加载，纪律要常驻上下文——写反了既费 token 又降低遵从率。口诀：一句话讲不清"何时触发"的，不配当 skill。
- **验证**：写完用触发句唤起，观察是否按步骤执行、关键步骤没有即兴发挥。
- **风险**：description 太宽会被误触发，太窄永远轮不到——参考 `research` 的写法（场景动词 + 产出物）。

### 玩法 6：嵌套 AGENTS.md 组织 SOP

- **目标**：利用 AGENTS.md 目录树分层协议，给不同子目录定制操作规程。
- **为什么值得玩**：根 AGENTS.md 管全局纪律，但"支付目录不许改 public 接口""docs 只许追加不许重写"这类局部 SOP 写进根文件会污染所有人上下文。协议是**深层优先、按需读取**：员工操作某目录时，该目录规程覆盖上层规程，且只有用到才读。
- **前置条件**：托管块 AGENTS.md 已同步（该产品的托管模板源在其提示词增强模板目录下的纪律增强模板）；记住——**子代理只继承 AGENTS.md + TOOLS.md，关键规则放 AGENTS.md，放 SOUL.md 子代理看不见**。
- **步骤**：在目标子目录新建 `AGENTS.md`，只写该目录的差异规程（触发条件、允许/禁止、完成定义），模板见 `recipes/sop-and-probes.md`。
- **验证**：让员工改该目录下一个文件，检查是否遵守局部规程（可先让它复述规程再动手）。
- **风险**：深层文件别重复全局纪律，只写差异——否则全局规则升级时，深层副本变成陈旧分叉。

### 玩法 7：双员工 A/B 测试

- **目标**：同一任务派给两个配置不同的员工（不同配方/不同推荐模型/Code Mode vs 默认模型），对比产出。
- **为什么值得玩**：模型与人格的手感无法从参数表读出，一次受控对比胜过十次道听途说。
- **步骤**：复制两个员工，一次只改一个维度；用 Team 的 parallel 模式同发（parallel 下互不可见，天然盲测）；按下表打分：

  | 维度 | 看什么 |
  | --- | --- |
  | 正确性 | 结论/代码是否对，能否跑通 |
  | 指令遵循 | 约束条件有没有被无视 |
  | 风格一致性 | 是否符合配方口吻 |
  | 信息密度 | 有没有注水 |
  | 可执行性 | 产出物能否直接用（diff 能否应用、文档能否照做） |
  | 成本 | token 消耗与耗时 |
  | 返工率 | 需要人接手的次数 |

- **验证**：至少攒 5 个任务再下结论，单次对比噪声太大。
- **风险**：结论随模型版本漂移——记录对比时的模型版本号，三个月重测一次。

### 玩法 8：Code Mode 深度玩法

- **目标**：判断何时让员工切到 ACP 编码代理（codeagent/opencode）承载的 Code Mode。
- **为什么值得玩**：Code Mode 与默认模型**互斥**——Code Mode 员工不消费默认模型额度；代价是能力面不同：编码代理强在长程代码任务，弱在开放式闲聊与广度知识。
- **决策表**：切 Code Mode——多文件重构、测试先行循环、长时间无人值守的实现任务、仓库级脚手架（如 `scaffold-exercises`）；留默认模型——调研、写作、评审、泛知识问答。
- **Usage 条目机制**：员工声明的可安装能力清单（Usage）分 openclaw / codeagent 两组，启用时只消费与运行时匹配的一组——给 Code Mode 员工配一堆 openclaw 条目，装了也不会消费。两边清单分别核对。
- **验证**：同一实现任务两种模式各跑一遍，按玩法 7 的表对比完成度、耗时与额度消耗；Code Mode 侧额外看三点——思考段是否成体系、工具调用步骤是否可追溯、正文结论是否与 diff 对得上（ACP 会话的三段过程流是免费的审计材料）。
- **风险**：互斥意味着"既要又要"得建两个员工（一个 Code Mode、一个默认模型），用 Team 串起来——这正是玩法 4 的生产线素材：让 Code Mode 员工当"实现工"坐 sequential 流水线下游时，注意单步超 2000 字会被截断，上游输出尽量要结构化短摘要；另外 ACP 会话不支持手动压缩，长任务提前拆好步，别让"实现工"一口气吞整仓。

## 三、U5 极客·布道者：生态与进化

### 玩法 9：darwin-skill 自进化

- **目标**：让员工定期评估并优化自己的技能库，形成"评估→改进→实测验证→人类确认→保留或回滚→成果卡片"的闭环。
- **为什么值得玩**：技能是文本资产，会腐化（仓库变了、依赖升了、描述过时）。该产品的 darwin-skill 技能把 SkillLens 9 维评分 + SkillOpt validation-gated 验证 + 独立评审 agent 打包成自动流水线，人类只在守关卡点头。
- **步骤**：每季度挑 3-5 个最常用的 skill 跑一轮；一次只改一个；改完用玩法 12 的回归集验收。
- **验证**：对比优化前后的评分卡与实测任务通过率，不看感觉看数字。
- **风险**：自动优化可能"更漂亮但不好用"——validation-gated 实测不过会自动回滚，但人类守关不能省；进化日志（git 历史）留档。

### 玩法 10：市场模板产品化

- **目标**：把调好的员工打包成市场模板运营：版本号、更新日志、管理"本地副本 vs 市场条目"的关系。
- **为什么值得玩**：你的配方（玩法 1/2/3 的产物）对别人也有价值，市场给了分发渠道。
- **合规三件套**：
  - **owner 是黄区编辑/上传的唯一权限依据**（产品内部架构决策记录语义）。
  - **更新资格只看 source=market**（产品内部架构决策记录语义）：本地有未发布编辑时拉取市场更新会**全量覆盖**本地改动——发布前先想清楚走哪边；source=user 的自建卡片（哪怕上传过市场）不支持拉取更新。
  - **roleId 指向系统预设 id 的员工禁止上传**（产品内部架构决策记录语义，硬堵门）：预设转换副本的 roleId 已清空，可编辑可删除但不可上传，别试图用它覆盖官方条目。导出 zip 的 `role-info.json` id 与上传载荷同源（`roleId || 员工id`），版本以市场条目为准。
- **步骤**：语义化版本（人格大改 major、配方调整 minor、错别字 patch）；每次发布写 changelog；导出前核对 role-info.json。
- **验证**：换台设备/账号走一遍"下载→更新"闭环，确认更新入口与覆盖行为符合预期。
- **风险**：上传 id 与市场条目碰撞会覆盖他人条目——产品内部架构决策记录语义已对导出/上传 id 做同源修复，别绕过应用内上传入口手工构造 payload。

### 玩法 11：组织级数字员工中台

- **目标**：多项目工作区复用同一批员工与 Team，把通用知识沉到员工身上而不是某个仓库里。
- **为什么值得玩**：员工绑定 backing Agent，Team 是全局实体、不绑定 workspace——对象模型天然支持"员工跟着人走，不跟着项目走"。
- **步骤**：
  1. 通用规矩进人格与 USER.md（跨项目生效），项目专属规矩进该仓库的 AGENTS.md（玩法 6），别混。
  2. cron + HEARTBEAT 定时巡检：HEARTBEAT.md 是运行时生成、跟踪 session 状态的文件，不受管也别手改；给员工排每日站会任务（例：每天 9:00 汇总昨日对话产生的待办）。
  3. 会话沉淀：长对话收尾跑 `knowledge-base`（后置知识库生成器，出带导航的 HTML 文档树），结论挂产品的 AI 导航 wiki 或项目 docs；跨会话交接用 `handoff`（脱敏后存系统临时目录，附建议技能清单）。
- **验证**：换一个新仓库，确认员工无需重新配置即可上岗，且记得你的全局偏好。
- **风险**：员工状态膨胀——每月清理 USER.md 过期条目与 wiki 死链；定时任务失败要有人看 HEARTBEAT 状态，别让 cron 静默空转。

### 玩法 12：自建评测回归集

- **目标**：给员工建任务回归集，每次改人格、换模型、升级版本后跑一遍，防退化。
- **为什么值得玩**：升级人格模板版本（该产品的人格包版本号，当前 5.4.0）会重写托管块。官方升级前有金丝雀验证（注入栈约 9.7k 字符预算 + 5 个行为探针），但**你的配方官方不负责**，自己的回归集自己建。
- **设计**（探针全文见 `recipes/sop-and-probes.md`；探针的规范版本另见本仓库 `probes/` 目录）：抄官方 5 个行为探针——不可信注入"停-引-问"、不编造工具、自称完成自检、压力下不谄媚、人格表达生效；再加自己的任务探针：每个高频任务留 1-2 道标准题 + 期望要点。
- **步骤**：回归集放 `.scratch/regression/`（沿用 issue tracker 规范）；改版后全量跑，记录通过率，退化先回滚配方再排查。
- **验证**：故意写一条讨好型错误配方，确认回归集能抓住。
- **风险**：回归集自身会过期——每季度淘汰过时探针，保持 20 题以内，跑得动才有价值。

### 统一红线（所有段位适用）

1. **不动运行时 Red Lines**：`AGENTS.md` 托管块内的红线段（破坏性操作确认等），人格配方不能绕过，SOP 不能覆盖。
2. **不上传 roleId 指向系统预设的员工**：产品内部架构决策记录语义（硬堵门），也是市场生态底线。

5. **密钥与隐私不进员工上下文**：Team 派发带原始用户消息，USER.md 与 cron 任务里都不放凭据；`handoff` 产物先脱敏。
