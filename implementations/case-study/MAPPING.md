# 案例研究映射：某闭源桌面客户端产品

> **方法论标注**：本文件是**闭源桌面客户端产品的作者自述案例研究**，未经独立验证；其中人格三件套部分已在 [../openclaw/MAPPING.md](../openclaw/MAPPING.md) 独立验证；Team/市场/Bastion/Code Mode 等产品治理特性为**待验证的设计主张**。文中出现的界面文案与版本号（如 v5.4.0）保留，因其为机制说明所必需。

本文件是《数字员工规范》（见 [../../SPEC.md](../../SPEC.md)）的案例研究映射，汇总某闭源桌面客户端产品（下称"该产品"）中各规范条目对应的落地事实，供对照一个真实产品理解条文。本文件不是规范的一部分，示例不构成规范要求。

## 1. 概述

该产品是一个 Electron 桌面客户端，作为 OpenClaw agent 运行时的 UI 客户端：它提供员工管理、对话、市场分发与治理门禁，实际执行由 OpenClaw 承载。本文件按规范章节逐层映射其落地事实；读者应注意其中 Team/市场/Bastion/Code Mode 等条目为作者自述、未经独立验证。

## 2. 对象链路（对应规范第 2 章：判定四要素）

该产品的领域模型与判定四要素逐一咬合，是"岗位说明书 → 在职员工 → 独立工位"的三段结构：

1. **Role（角色模板）**：名称 / 描述 / 指令 / 推荐模型，是岗位说明书，**不可对话**。Role 模板从产品的角色模板目录加载（产品主进程中的角色管理器负责 `loadRoleTemplate`），物化为员工时套用人格七件套增强；市场安装的角色同样走 Role → Employee → Agent 链路口径。
2. **Employee（数字员工）**：Role 的持久实例化，可对话、有持久状态，绑定一个 backing Agent。员工是组织的资产单元，也是市场分发与版本审计的单位。
3. **Agent**：OpenClaw 隔离执行单元，每个员工独占独立 workspace 与 agentDir——"独立工位"。

另有**虚拟默认助手**：未绑定员工的主 agent 会话在侧边栏归入一个虚拟节点（产品前端侧边栏树视图与会话分组模块），保证无员工绑定的会话也有清晰的归属呈现。

Code Mode 下员工改由 ACP 编码代理（codeagent / opencode）承载、与默认模型互斥——同一岗位可由不同工种的干法承接，对象链路不变。

## 3. 人格七件套落地（对应规范 3.1 人格层、第 5 章可移植性标准）

人格资产集中在产品的提示词增强模板目录（v5.4.0），经产品主进程中的受管块同步器以**受管块**（managed block）方式同步到 `~/.openclaw/workspace/`。七件套分工如下（★ 为受管块同步的六个文件）：

| 工作区文件 | 模板来源 | 职责 |
|---|---|---|
| ★ SOUL.md | `soul-enhancement.md` | 人格、语气、边界、信任模型 |
| ★ AGENTS.md | `capabilities-enhancement.md` | 操作指令、MCP 纪律、完成规则、认识论纪律、Red Lines 红线 |
| ★ TOOLS.md | `tools-enhancement.md` | 本地 MCP 事实与配置链（环境事实，非策略） |
| ★ IDENTITY.md | `identity-enhancement.md` | 最小身份记录 |
| ★ USER.md | `user-enhancement.md` | 最小用户画像记录 |
| ★ BOOTSTRAP.md | `bootstrap-enhancement.md` | 首跑 / 缺工具时的诊断提示，不承载长期策略 |
| HEARTBEAT.md | —（OpenClaw 运行时生成） | 会话状态跟踪；不经受管块同步 |

产品主进程中的角色管理器维护七件套到增强模板的完整映射；受管块更新满足规范 5.6 的四条约束：缺失则插入、旧版原位替换、块外用户内容保留、同版本重跑幂等（版本门由人格包版本号驱动）。

两个关键设计原则，即规范 3.1"人格与纪律分离"的工程依据（这两条是 OpenClaw 原生机制，可独立验证，见 [../openclaw/MAPPING.md](../openclaw/MAPPING.md)）：

- **子代理只继承 AGENTS.md + TOOLS.md**：子代理不读 SOUL.md，因此子代理关键规则（MCP 纪律、红线、完成规则）必须放进 AGENTS.md；放进 SOUL.md 会被子代理绕过。Red Lines 正是借此约束随每一次委派下沉传播。
- **AGENTS.md 目录树分层、深层优先**：深层文件覆盖浅层冲突，按需读取，根文件保持精简，避免吃光上下文窗口。

**金丝雀（canary）发布**：人格包升级（如 v5.4.0）前先指向一个测试工作区验证三点——(1) 注入栈总量约 9.7k 字符；(2) 行为探针四件套全过：不可信输入"停—引—问"止损、不虚构工具、完成自检（不谎报 done）、压力下反谄媚，另加 SOUL 标记改名检查；(3) `<<<SUGGESTED>>>` / `<<<END_SUGGESTED>>>` 哨兵页脚渲染正确。探针全过才晋升全量，并由受管块同步器的单元测试版本断言与字符上限测试固化。发布规范见产品提示词增强模板目录的说明文档。

## 4. 能力层（对应规范 3.2）

- **Usage 条目**：Role / Employee 声明式能力清单，分 openclaw / codeagent 两组；启用时只消费与当前运行时匹配的一组——能力装配与运行时解耦，正是规范"按岗位装配、按运行时匹配、按版本审计"条文的实现。
- **技能库**：产品仓库中的技能库（数十个，白皮书统计时为 47 个，此后持续增长），与 Usage 声明互补。
- **Code Mode 能力切换**：员工由 ACP 编码代理承载时，能力消费切至 codeagent 组，Usage 声明不变。

## 5. 知识层（对应规范 3.3）

- **组织知识三件套**：产品的 AI 导航 wiki、工程文档档案、仓库根目录的领域术语表，对应规范 3.3 的组织知识——档案与术语可沉淀、可检索、可继承。AI 导航 wiki 由维护流程持续更新，是 agent 进入仓库后的第一导航入口。
- **长期记忆**：运行时工作区 `MEMORY.md` 承载员工的跨会话长期记忆。
- **岗位知识复用**：市场模板把岗位知识（指令、技能、知识文件）组织化分发，实现岗位知识的组织级复用；副本与继任者安装同一模板即继承岗位知识。

## 6. 运行时层（对应规范 3.4）

> 本节为**待验证的设计主张**（作者自述）。

- **Team**：多员工命名组合，支持 parallel / sequential 两种派发模式。Team 会话使用独立 session key `team:{teamId}:{agentId}:main`，与 1:1 员工会话完全隔离；parallel 模式下 Agent 间互不可见（独立视角避免锚定效应），sequential 模式单向可见（上游输出拼入下游输入）。派发结果有 5 种目标状态（dispatched / failed / blocked / unavailable / skipped）。
- **Bastion**：安全层对消息做**消息级**安全检查，Team fan-out 前统一过检——对应规范 4.5 / 6.x 的协作消息级安全检查。
- **Code Mode**：员工对话经 ACP 对接 opencode 编码代理，由 acp-bridge 插件实现（不修改 OpenClaw 源码，全部走 Plugin SDK 公开 API）；思考、工具调用、正文三段实时流出——过程可见性本身就是治理能力。限制：ACP 会话不支持手动压缩；Lite（精简模式）默认启用。设计见产品的一份 ACP 桥接设计文档。
- **控制面**：Gateway / Bastion / MCP 构成控制面——Gateway 管能力路由与调用，Bastion 管安全拦截，MCP 管工具接入标准化。

## 7. 治理层（对应规范 3.5、第 6 章）

> 本节为**待验证的设计主张**（作者自述）。

- **公司规章**：产品仓库根纪律文件即组织级纪律文件，内置 TDD 工作流、统一交付门禁（lint + typecheck + test + 打包）、i18n 合规、commit 规范等；ESLint 规则防止渲染层 Node 模块泄漏到前端产物。
- **发布门禁**：统一交付门禁脚本（lint + typecheck + test + 打包）是交付前的统一回归门禁——人格包、技能集、代码任何变更全绿才允许进入发布，与规范 7.3"回归集"同构。
- **术语表**：产品仓库的领域术语表维护领域术语，全库统一词汇。
- **决策档案**：产品内部的两条架构决策记录（ADR）及其所在的决策档案目录，保证决策可审计、可回溯。
- **分发治理**：市场分发以 owner 为编辑 / 上传唯一权限依据；市场条目版本为唯一版本来源（不信任包内自声明版本，防元数据漂移）；上传 id 与导出 zip 内 id 同源（`roleId || 员工id`），堵住覆盖洞。
- **错误枚举化**：Team 派发结果将内部错误映射为有限枚举（gateway_unreachable / bastion_blocked / sequential_step_failed 等），禁止原始错误消息外泄。

## 8. 成熟度自评（对应规范第 4 章）

按白皮书自评（作者自述）：单个 Employee 具备 **L3** 能力（多步任务 + 工具组合 + Bastion 前置检查 + 追问澄清）；Team 的 parallel / sequential 派发与 5 种目标结果状态已搭出协作骨架。按联合门槛规则，治理与评测未升档前不作 L5 自评。尚未补齐的部分（V2 规划）：Team 引入 selector（LLM 路由）派发、Agent 间共享上下文开关、per-target Bastion 策略、Team 模板经市场分发——协作形态初备，治理与评测仍待补齐。
