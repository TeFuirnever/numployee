本文件是《数字员工规范》（见 [../../SPEC.md](../../SPEC.md)）的参考实现映射，把规范各章机制性条目逐条对应到 OpenClaw 原生机制。读者可在 OpenClaw 公开仓库中逐项核查；本文件不是规范的一部分，示例不构成规范要求。

## 1. 对象链路（对应规范第 2 章：判定四要素）

OpenClaw 提供"执行单元"这一原生对象：每个 agent 拥有独立的 workspace 与 agentDir（agent 目录），是会话隔离与状态持久化的最小单位。规范的对象链路据此落成三段：

1. **Role（角色模板）**：名称 / 描述 / 指令 / 推荐模型，岗位说明书，**不可对话**——纯配置对象。
2. **Employee（数字员工）**：Role 的持久实例化，绑定一个 backing Agent，可对话、有持久状态。
3. **Agent**：OpenClaw 隔离执行单元——"独立工位"，员工独占 workspace 与 agentDir。

持久身份、可装配能力、可沉淀知识三要素落在 workspace 文件上，可治理红线落在纪律文件并随继承协议传播（见第 3 节）。

## 2. 工作区七件套（对应规范 3.1 人格层、第 5 章可移植性标准）

OpenClaw 工作区原生提供 SOUL.md / AGENTS.md / TOOLS.md / IDENTITY.md / USER.md / BOOTSTRAP.md / HEARTBEAT.md 七件套：

- SOUL.md：人格、语气、边界、信任模型；
- AGENTS.md：操作纪律、工具纪律、完成规则、红线；
- TOOLS.md：本地环境事实与配置链（环境事实，非策略）；
- IDENTITY.md：最小身份记录；
- USER.md：最小用户画像记录；
- BOOTSTRAP.md：首跑 / 缺工具时的诊断提示，不承载长期策略；
- HEARTBEAT.md：会话状态跟踪，由运行时生成。

这七件套的职责划分即规范"人格三件套分离"（规范 5.1-5.2、5.5）的参照基准：人格文件不放操作流程，环境事实与策略分文件。

## 3. 继承协议与子代理纪律（对应规范 3.1 分离原则、5.4 继承协议）

OpenClaw 的两条原生继承规则，是规范"人格与纪律分离"原则与推论的直接工程依据：

- **子代理只继承 AGENTS.md + TOOLS.md**：子代理不读 SOUL.md。推论：子代理关键规则（工具纪律、红线、完成规则）必须放进 AGENTS.md；放进 SOUL.md 会被子代理绕过。
- **AGENTS.md 目录树分层、深层优先**：深层文件覆盖浅层冲突，按需读取，根文件保持精简，避免挤占上下文窗口。

## 4. Session key 模型（对应规范 3.4 运行时层、4.3 会话隔离）

OpenClaw 以 session key 标识会话；员工会话采用 `agent:{agentId}:main` 式的 key 命名空间。多员工并存时各 key 独立，数据面互不可见——规范 4.3"会话隔离"的对照实现；谁发起、谁执行、在哪个会话内，均可由 key 重建（对应第 6 章审计留痕）。

## 5. 金丝雀发布（对应规范 7.3 回归集）

OpenClaw 支持以测试工作区先跑新配置、验证通过再切换正式工作区的发布方式（canary 金丝雀）。规范 7.3"升级后跑固定回归集，全绿才允许发布"的可执行化路径：新配置指向隔离工作区 → 跑行为探针与任务回归 → 全量晋升。注入栈字符预算、探针判定与版本断言由实现方按 7.2/7.3 自建。

## 6. 边界说明

Team 多员工编排、市场分发、消息级安全拦截、ACP 桥接编码代理等产品治理特性**不是** OpenClaw 原生机制；一个闭源桌面客户端产品的设计主张以作者自述案例归档于 [../case-study/MAPPING.md](../case-study/MAPPING.md)（未经独立验证）。本映射仅覆盖可在 OpenClaw 公开代码中验证的机制条目。
